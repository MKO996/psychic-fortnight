# Decisions

One line per decision, and why. Newest at the bottom of each phase.

## Setup
- Project lives in `rungs/` because the repo root already holds another project (LEFT); keeps both untouched.
- Expo SDK 58 (`expo@58.0.25`, React Native 0.88, React 19.3): the current stable on npm on 2026-11-16, via `create-expo-app@latest --template default`.
- Skills installed with the skills CLI (`npx skills add`): frontend-design, expo-overview, expo-native-ui, expo-dev-client, expo-animation, expo-router, vercel-react-native-skills. Committed so every future session has them.
- Expo README prefers `claude plugin install expo@claude-plugins-official`; that can't run from inside a session, so the CLI route was used. The template's `.claude/settings.json` also enables that plugin for local Claude Code.
- `docs.expo.dev` and `api.expo.dev` are blocked in the cloud build environment: docs are read from the `expo/expo` GitHub source, and installs use `EXPO_OFFLINE=1 npx expo install` (same version table, bundled in the `expo` package).
- Jest via `jest-expo` preset (Expo's documented setup), so later UI tests use the same runner as engine tests.

## Phase 1 — Engine
- Engine is pure TypeScript in `src/engine/`, no React imports: testable in milliseconds and reusable by all transports.
- Word source: ENABLE (public domain), 3–5 letters only.
- Three word tiers instead of one list: `endpoint` (START/TARGET) ⊂ `path` (used for PAR) ⊂ `valid` (accepted moves). Par uses only common words so it is always fair; rare valid words let a clever player go *under* par.
- Rarity filter = word frequency (`wordfreq` 3.1.1, Zipf scale): valid ≥ 1.5, path ≥ 3.0, endpoint ≥ 3.5. Thresholds picked by sampling words around each cut-off, not guessed.
- Frequency alone is noisy (names like "dee", "fiat" score high), so hand-curated `path-exclude.txt` and `endpoint-exclude.txt` fix the worst cases. Grow these lists whenever a puzzle feels unfair.
- Plurals and simple verb forms (cats, baked) never become START/TARGET: base words make better puzzles.
- Family-friendly: LDNOOBW list (CC-BY 4.0, credit needed in the app's About screen) + our `extra-blocklist.txt`. Inflections are blocked too, after an audit found "shits"/"cunts" passing a base-word-only filter.
- Word data is generated by `scripts/build_words.py` and the JSON output (56 KB) is committed: the app and tests never need Python or the internet.
- Graph built with the "bucket" trick (`_ish` → fish, dish, wish): O(n·L) instead of comparing every pair. Built lazily, cached; ~16 ms on a laptop.
- Generator picks START, runs BFS, then picks TARGET from the reachable words at the right distance: solvable by construction, par known exactly.
- Difficulty: easy = 3–4 letters, par 3–4; medium = 4 letters, par 5–6; hard = 5 letters, par 5–8. Measured: thousands of puzzles exist for every combination.
- Seeded PRNG (Mulberry32) + FNV-1a hash of `rungs-daily-v1:YYYY-MM-DD`: same daily puzzle on every device, offline.
- Daily uses the player's LOCAL date (like Wordle): each person's new puzzle arrives at their midnight.
- Daily difficulty by weekday: Mon–Tue easy, Wed–Fri medium, Sat–Sun hard (people have more time at weekends).
- Daily #1 = 2026-11-16 (`DAILY_EPOCH`). May change before release; must never change after.
- Golden snapshot test pins known daily puzzles: any change to words or generator that would change "today's puzzle" fails loudly.
- Hint = shortest route avoiding used words, common words first, then any valid word; reveals only the letter position. Returns `stuck` when no route exists (UI will suggest erasing a rung).
- Added `eraseLast` (undo) to the engine: on a real whiteboard you can wipe a rung, and without it a player can get permanently stuck. Score = final ladder length, so erasing can't be used to cheat.
- Move errors are typed (`not-a-word`, `already-used`, …) instead of a boolean, so the UI can react differently to each.
